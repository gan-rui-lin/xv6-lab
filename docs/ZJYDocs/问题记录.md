### uart里的参数是如何确定的
参数主要来源于 ==16550 UART== 芯片的数据手册和硬件规范，具体如下：

1. UART寄存器地址和编号
- UART0：在 memlayout.h 中定义，表示 UART 的基地址（如 0x10000000）。
- Reg(reg)：通过基地址加上寄存器编号偏移，定位到具体寄存器。
2. 各寄存器编号
- RHR/THR = 0：接收/发送寄存器，编号为0。
- IER = 1：中断使能寄存器，编号为1。
- FCR/ISR = 2：FIFO控制/中断状态寄存器，编号为2。
- LCR = 3：线路控制寄存器，编号为3。
- LSR = 5：线路状态寄存器，编号为5。
这些编号都是16550 UART芯片手册规定的。

3. 各寄存器位定义
- IER_RX_ENABLE (1<<0)：使能接收中断。
- IER_TX_ENABLE (1<<1)：使能发送中断。
- FCR_FIFO_ENABLE (1<<0)：使能FIFO。
- FCR_FIFO_CLEAR (3<<1)：清空FIFO。
- LCR_EIGHT_BITS (3<<0)：8位数据位。
- LCR_BAUD_LATCH (1<<7)：进入波特率设置模式。
- LSR_RX_READY (1<<0)：接收缓冲区有数据。
- LSR_TX_IDLE (1<<5)：发送缓冲区空，可以发送新数据。
这些位的含义和用途同样来自芯片手册。

4. 波特率设置
- WriteReg(0, 0x03) 和 WriteReg(1, 0x00)：设置波特率除数为3（低字节）和0（高字节），对应38400波特率（假设UART时钟为1.8432MHz）。
- 具体波特率计算公式：波特率 = UART时钟 / (16 * 除数)。
5. 其他参数
- tx_lock、tx_busy、tx_chan：用于内核并发和同步，保证多进程/中断下串口输出的正确性。

### relocation truncated to fit
**问题描述：**
> ob@ob-VirtualBox:~/task/riscv-os$ make all
> riscv64-unknown-elf-gcc -march=rv64g -mabi=lp64 -nostdlib -nostartfiles -g -Wall -I../../include -c -o kernel/boot/main.o kernel/boot/main.c
> riscv64-unknown-elf-ld -T kernel/boot/kernel.ld -o kernel/kernel.elf kernel/boot/entry.o kernel/boot/uart.o kernel/boot/main.o
> kernel/boot/main.o: in function main': /home/ob/task/riscv-os/kernel/boot/main.c:3:(.text+0x10): relocation truncated to fit: R_RISCV_HI20 against .LC0'
> make: *** [Makefile:14：kernel/kernel.elf] 错误 1

**解答:**
> 你遇到的 relocation truncated to fit: R_RISCV_HI20 against '.LC0' 错误，是因为在***裸机（无操作系统、无C运行时）环境下，直接访问全局/静态数据或字符串字面量时，编译器默认的寻址方式（如 auipc/addi）无法访问高于 2^20 字节的地址空间***（即不能跨越 1MB 边界），而你的链接脚本把内核放在了 0x80000000，远超 1MB。

**解决方法：**

>在编译时加上 -mcmodel=medany，让编译器用适合高地址的寻址方式。
修改 Makefile 的 CFLAGS，加上 -mcmodel=medany。
例如：
`CFLAGS = -march=rv64g -mabi=lp64 -mcmodel=medany -nostdlib -nostartfiles -g -Wall -I../../include`
然后重新 make 即可解决该问题。
>原因简述：
-mcmodel=medany 让编译器生成的代码可以访问任意高地址的数据和字符串常量，非常适合裸机RISC-V内核开发。


### 物理内存分配的初始化参数确定

```c
void pmm_init() {
  extern char end[];  // first address after kernel loaded from ELF file
  char *p = (char *)((unsigned long)end + PAGE_SIZE - 1);
  p = (char *)((unsigned long)p & ~0xfff);  // align to page boundary
  freelist = 0;
  while ((unsigned long)p < PHYSTOP) {
    free_page(p);
    p += PAGE_SIZE;
  }
}
```
**问题描述：**
> 源代码里这个end的数据是怎么得来的

**回答：**
你的问题非常好，**`end` 这个符号在 C 代码里是怎么得到数据的？它的值是谁“决定”的？**

---

## 1. **`end` 是链接器生成的符号，不是C代码自动决定的**
- 它不是函数，不是变量，也不是 C 编译器分配的。
- 它是 **链接脚本（如 kernel.ld）里用 `PROVIDE(end = .);`** 这样声明的“符号”。

---

## 2. **`end` 的值如何被确定**

### 关键在于**链接脚本**，比如：
```ld
. = 0x80000000;

.text : { ... }
.rodata : { ... }
.data : { ... }
.bss : { ... }

. = 0x80010000;
PROVIDE(end = .);
```

- “**.**” 是此时的地址指针，表示所有前面的段整体用完后的位置。
- `PROVIDE(end = .);` 就让符号 `end` 指向这里，也就是**内核所有代码、数据、bss和（如果有）栈与堆预留后的下一个物理内存地址**。

---

## 3. **C代码中如何使用 `end`**

你可以在 C 文件里用：
```c
extern char end[];
```
- 这代表 `end` 是一个在链接后由链接器决定、可当作地址用的符号。
- `end` 的数值就是链接脚本里定义的位置，通常是内核自身所有内容用掉后的尾地址。

---

## 4. **为什么这么做？**

- 你的物理内存分配器要**避免把自己的分配覆盖内核本身**（包括代码、数据、bss、堆、栈）。
- 只要“从 `end`（对齐到页边界后的位置）开始，向后一直到物理内存上限 PHYSTOP”，就是不会和内核空间冲突的全部可分配空间。

---

## 5. **流程总结**

- 编译阶段：每个段的大小、顺序都由链接脚本布局。
- 链接完成后：`end` 符号被定位在所有段结束（.、栈、堆等）之后。
- 运行时：C代码用 `extern char end[]` 就可以获得这个物理地址，“从这里往后”安全分配页面。

---

## 6. **验证方法**

编译后用`nm`检查你的内核镜像，可以看到类似：

```
$ nm kernel.elf | grep end
80010000 B end
```
这里`end`的值就是0x80010000。

---

## 总结

- **`end`本质上是链接器脚本计算出的变量，代表了你的内核镜像占用了多少物理空间的“终点”。**
- 它能确保你分配的物理页面绝不会和内核自身占用的空间重叠。


### 为什么页表的地址开始时是 0x87FFF000

页表的地址（比如你调试输出里看到的`0x87FFF000`）其实就是通过物理内存分配器`alloc_page()`获得的一块**可用的物理页的起始地址**，和你设置的物理内存分配策略与内存布局有关。


#### 1. 页表本质
- 每个页表（无论是根表、二级、三级，每一级）在RISC-V下都实际存储在物理内存的**一页（4KB）**里。
- 分配页表时，用`alloc_page()`从空闲页链表分配出一块4KB空间。

#### 2. 为什么分到这个具体地址？
- 你在`pmm_init()`（物理内存管理初始化）中，从一块较高的物理地址开始，按页为单位向上递增，每 free 一页其实把它链入一个空闲链表。
- 你第一次 alloc_page 默认返回 freelist 的第一个节点，结果就是初始化时最后一个被 free_page 的地址（也就是最高的那一页）！

比如，假设你的内存布局如下：
- KERNBASE = 0x80000000
- PHYSTOP = 0x88000000
- 你的内核最后是`0x88000000-4K`，你一页页往上 free，最后一次 free 的是`0x87FFF000`。
- 所以链表头就是0x87FFF000，所以第一次分配总拿 head，所以刚好就是 0x87FFF000！

#### 3. 总结
- **页表地址由物理内存分配器分配决定，通常是最高可用物理空间开始向下分配，导致第一次alloc就分配到最高的一页。**
- 没有特殊“魔力”，它只是你物理内存池里可用的一个整页地址。

---

#### ⚠️ 温馨提示：
- 下次再建第二个页表时，继续往下一个可用地址，比如 0x87FFE000，再下一个 0x87FFD000……这样整个内存池会被“倒着”用下去。
- 这个地址对物理可用性唯一要求是“字对齐、在合法物理空间中”。

---

**一句话总结：**  
页表的起始地址（如`0x87FFF000`）就是分配器能给到你的第一个空闲物理页面的高地址——即高端物理内存的一页，被用来存放页表内容。
